# Intentional technical debt

Each entry has an owner and a removal trigger (CLAUDE.md rule 13). Debt without a trigger is not
accepted.

| Id | Debt | Why now | Owner | Removal trigger |
|---|---|---|---|---|
| TD-001 | Local/CI PostgreSQL image is built from `docker/postgres/Dockerfile` on every fresh CI runner (~1–2 min, then cached per runner). The base is now pinned by manifest-list digest (IG0-M01), but the `postgresql-17-pgvector` apt package is resolved at build time, so the built layer is not bit-reproducible. | No maintained upstream image ships both PostGIS and pgvector; publishing our own image needs a registry decision. | dev | Push a built image to GHCR from a workflow and pull it by digest in Testcontainers/compose, when CI time matters or a second contributor joins; that also pins pgvector. |
| TD-002 | Tenant entitlements are rows in `app.tenant_capability` written at tenant creation from `DEFAULT_PLAN_ENTITLEMENTS` (the catalogue's non-extension keys); there is no `plan` / `plan_entitlement` table yet. | No billing or plan concept exists in Slice 0. | dev | Billing/plan slice: introduce `plan` + `plan_entitlement`, derive `entitled` from the plan, keep the column as a materialised cache or drop it. |
| ~~TD-003~~ | ~~The domain package depends on `@eia/db`.~~ **Resolved at Implementation Gate 0 (IG0-B02).** Orchestration moved to `packages/application`; `packages/domain` is pure and the boundary is enforced by ESLint plus `packages/domain/test/purity.test.ts` (ADR-015). | — | — | Closed 2026-09-01. |
| TD-004 | Project capability rows only restrict; the database has no trigger preventing an `enabled = true` override row for a key the tenant lacks (the resolver's AND and the write-time guard cover it). | Trigger logic would duplicate the resolver in SQL. | dev | If a second writer (import, admin tool) can create override rows, add a constraint trigger mirroring `assertProjectOverrideAllowed`. |
| TD-005 | Client Portal DB role (`eia_portal`) and `portal` schema are not created; migration 0000 reserves the role name only. | Portal is Slice 7 (ADR-009); an unused role widens surface. | dev | Client Portal slice: create the role, schema, grants and RLS with its own isolation tests. |
| TD-006 | Foundation UI (sign-in, tenant/project context pages) uses a CSS module and inline forms; no `packages/ui` components exist yet. | Slice 0 forbids product screens; components arrive with Portfolio/shell. | dev | Portfolio slice: replace foundation pages with the shell and `packages/ui` primitives; keep `/health` and the capability probe route. |
| TD-007 | Better Auth runs with the runtime role's CRUD grants on the `auth` schema (no RLS there; tables are not tenant-scoped). Session lookups therefore trust Better Auth's own row filtering. | Identity tables have no tenant column by design (ADR-010). | dev | Review at the compliance gate; consider a dedicated `eia_auth` role if the auditor requires separation between identity and operational data access. |
| TD-008 | Membership removal and last-owner protection on removal are not implemented (only role change is). | Tenant Settings › Usuarios arrives with the Portfolio/shell slice. | dev | Implement `removeTenantMembership` with the last-owner rule, cascade semantics and audit when that surface is built. |
| TD-009 | `eia_readonly` (BI) role from ADR-004 is not created. | No consumer. | dev | First analytics/BI requirement. |
| TD-010 | **Deferred onboarding work, no longer an exposed failure mode.** Public self-signup is disabled (IG0-H01), so the non-transactional Better Auth sign-up path is unreachable by anonymous callers. Creating an identity together with the application user, `TenantMembership` and optional `ProjectMembership` still has no atomic or compensating workflow; identities are provisioned deliberately meanwhile. | Signup is closed; the gap is now in future onboarding, not in a live endpoint. | dev | Onboarding slice: design provisioning (invitation → identity → app user → membership) with a compensating or transactional path and reconciliation for partial failures, then decide whether to re-open self-signup. |
| TD-011 | In development the Better Auth instance is recreated per request (`NODE_ENV=development`) so schema hot reloads are picked up; production caches it on `globalThis`. | Dev ergonomics after the `issuer` schema change. | dev | Remove when the auth schema is stable (after Slice 0 review) if the per-request cost is noticeable. |
| TD-012 | The Postgres host port for docker-compose is `EIA_PG_PORT` (default 5433) because 5432/5433 were occupied on the developer machine; CI uses Testcontainers on random ports. | Machine-specific conflict. | dev | None required; documented in README and `.env.example`. |
| TD-013 | Migration drift check (`db:check`) runs `drizzle-kit generate` and cleans up; a native `drizzle-kit check`-style drift command would be lighter. | drizzle-kit 0.31 lacks a no-write drift command for this setup. | dev | When drizzle-kit ships a dry-run diff. |
| TD-014 | Branch protection / rulesets for `main` cannot be configured: the repository is private on a GitHub Free personal plan (API returns 403 "Upgrade to GitHub Pro or make this repository public"). Squash-only merge and delete-branch-on-merge are set; PR-required, required checks, linear history and force-push blocking rely on developer discipline and CI until then. | GitHub plan limitation; the repository must stay private. | dev | Upgrade to GitHub Pro (or move the repository to an organisation plan), then apply the ruleset in DEPLOYMENT.md §7 with contexts `quality` and `db`. |
| TD-015 | Project profile defaults are resolved from the in-code system-profile registry via the project's `profile_key`; an unknown key contributes no defaults (falls through to enabled, still under the tenant ceiling). Profile *versions* are recorded but not yet used to select a historical default set. | One system profile exists; versioned profile snapshots arrive with the project-profile slice. | dev | Project-profile slice: persist the profile snapshot (or a versioned registry) and resolve defaults by `profile_key` + `profile_version`. |
